# Change: devshell-activation-contract

## Why

The devshell "activation" surface is the boundary where xi transitions a user's
plain shell into a devshell subshell with the flake's environment applied. Today
this surface is spread across four modules:

- `activate.rs` — generates the shell rc snippet that installs the prompt hook
  (`xi develop activate {bash,zsh,fish}`).
- `enter.rs` — the synchronous `xi develop` entry command that builds, evals,
  and execs a subshell.
- `subshell.rs` — the spawn-command generator that fires up the child shell with
  the correct sentinel + depth env vars.
- `env_file.rs` — writes the actual `env.sh` / `hook.sh` files that the child
  shell sources.

There is a **contract** between these modules — env-var names (`__XI_*`), exit
codes (200 = cd-out), depth-scoped injected-var registries, PATH
prepend-not-replace semantics, sourced-file layout — but it has never been
specified. As a result:

- Regression fixes to one module have historically broken another (e.g. a fix in
  `env_file.rs`'s cleanup broke `subshell.rs`'s nesting because the registry key
  changed).
- Adding a new shell (currently: bash, zsh, fish; requested: nushell) means
  reverse-engineering the contract from four modules.
- The prompt-hook budget work in `xi-devshell-daemon` implicitly relies on
  `__XI_IN_DEVSHELL` and `__XI_LOCK_HASH` being set correctly by activation —
  but nothing enforces that.

## Verified Against Current Code (2026-11-07)

Re-read against `activate.rs`, `subshell.rs`, `env_file.rs`, `enter.rs`,
`hook/shortcut.rs`, and the response-builder region of `daemon/server.rs`
(around lines 630-697):

- **Missing entirely from the prior proposal**: a daemon-mediated re-source
  protocol sits alongside the four static modules. The daemon tracks
  per-consumer-pid generations via `shell_registry` (`reg.should_source_env`,
  `reg.should_source_hook`, `reg.mark_sourced_env`, `reg.mark_sourced_hook` in
  `daemon/server.rs`) and exposes env/hook files through a stable
  current-symlink indirection
  (`dirs::current_link(state_dir, "env-<target>", "sh")` / `"hook-<target>"`).
  The wire format is `PromptResponse` (`should_source_env`, `env_file_path`,
  `should_source_hook`, `hook_file_path`, `should_exit`, `notifications`,
  `daemon_state`, `is_trusted`), and the actual re-source/exit-trap shell code
  is generated by `prompt.rs::generate_subshell_output`, not by `env_file.rs`
  alone. This is now specified below as its own requirement.
- **SKIP_VARS was understated**: the real list in `env_file.rs:9-50` has 28
  entries, not the
  `HOME, USER, SHELL, TERM, SSH_AUTH_SOCK, WAYLAND_DISPLAY,
  etc.` shorthand
  previously used. Now reproduced in full and made normative below.
- **`__XI_ORIG_PATH` has no writer anywhere in the codebase.** It is read once,
  in `trust.rs:35`, purely to decide whether to print shell-config setup
  instructions; nothing exports it into a child shell. The "de-activation is a
  subtraction, not a lookup" mechanism this proposal previously described does
  not exist. The real mechanism is pure process isolation: the child shell exits
  and the parent process resumes with whatever environment it already had,
  because the parent was never mutated (see `subshell.rs`'s module doc: "Exit,
  child dies, parent resumes with original clean env"). Rewritten below; a task
  is added to either wire `__XI_ORIG_PATH` for real or delete the dead check.
- **`__XI_LOCK_HASH` has no writer anywhere in the codebase either.**
  `hook/shortcut.rs` defines `ENV_LOCK_HASH` and reads it from the process env
  for the prompt-tick shortcut fast path, but grepping the full production code
  path (`env_file.rs::generate_content`, `subshell.rs::generate_spawn_command`,
  `prompt.rs::generate_subshell_output`) turns up no `export`/`set_var` of it
  outside `shortcut.rs`'s own unit tests. The shortcut fast path can therefore
  never fire in production today. Flagged as a new P1 task.

## What Changes

- Introduce capability `xi-devshell-activation` that owns two layers of the
  activation contract: the static per-shell contract (env vars, exit codes, PATH
  discipline, SKIP_VARS, build-var exclusion, script minimality, shell adapter
  surface), and the daemon-mediated re-source protocol described in its own
  requirement below.

  - **Well-known env vars** the activation surface publishes into the child
    shell: `__XI_IN_DEVSHELL`, `__XI_FLAKE_ROOT`, `__XI_BIN`, `__XI_DEPTH`,
    `__XI_INJECTED_VARS_<depth>`, `__XI_SUPPRESS`. Names, semantics, lifetimes,
    and cleanup ownership documented below. `__XI_LOCK_HASH` and
    `__XI_ORIG_PATH` are named in code (`shortcut.rs`, `trust.rs`) but, per the
    verification notes above, neither is currently exported into the child shell
    by any writer; they are listed here as planned/gap items, not as
    currently-published variables, until the new tasks below land.

  - **Exit-code conventions** the subshell/hook boundary agrees on:
    - `200` means the shell exited because CWD left the flake root; the parent
      MUST NOT set the suppress flag and MUST allow re-entry on the next `cd`
      in.
    - any other non-zero (including a plain `exit` with code `0`) means the user
      explicitly exited the shell; the parent MUST set
      `__XI_SUPPRESS=<flake_root>` to prevent an immediate re-entry loop. The
      suppress flag clears on `cd` out then back in.

  - **PATH discipline**: `env.sh` MUST prepend nix paths to `$PATH` and MUST NOT
    replace or reorder existing entries. De-activation happens through process
    isolation (the child shell exits and the parent's original, never-mutated
    environment resumes), not through a captured-and-subtracted
    `__XI_ORIG_PATH`; this proposal previously asserted the latter incorrectly.

  - **Depth-scoped cleanup registry**: nesting devshells MUST NOT cause a child
    to clean up the parent's injected vars on exit. The registry env var MUST be
    `__XI_INJECTED_VARS_<depth>` where `<depth>` = current `$__XI_DEPTH`. Each
    level owns and cleans exactly its own registry.

  - **SKIP_VARS invariant**: the full, normative list of env vars that MUST NOT
    be overwritten by the devshell env, reproduced verbatim from
    `env_file.rs:9-50`: `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `COLORTERM`,
    `TERM_PROGRAM`, `DISPLAY`, `WAYLAND_DISPLAY`, `XDG_SESSION_TYPE`,
    `XDG_RUNTIME_DIR`, `XDG_DATA_DIRS`, `DBUS_SESSION_BUS_ADDRESS`,
    `SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `LANG`, `LANGUAGE`, `LC_ALL`, `LC_CTYPE`,
    `TZ`, `PAGER`, `EDITOR`, `VISUAL`, `PWD`, `OLDPWD`, `SHLVL`, `TMPDIR`, `_`.
    `PATH` is handled by the prepend logic above, not by this skip list.

  - **Nix build-time vars discarded**: `NIX_BUILD_TOP`, `NIX_LOG_DIR`,
    `NIX_BUILD_CORES`, `NIX_ENFORCE_PURITY`, `NIX_ENFORCE_NO_NATIVE`,
    `NIX_STORE`, `TEMP`, `TEMPDIR`, `TMP` MUST NOT leak into the interactive
    shell.

  - **Activation script minimality**: the `xi develop activate <shell>` output
    MUST be a small, static snippet that (1) locates the xi binary, (2) defines
    a prompt hook, (3) installs it, with no flake detection, no trust logic, and
    no env manipulation in generated shell code. All decisions live in the Rust
    binary.

  - **Daemon-mediated re-source protocol** (new to this spec; currently
    undocumented, already implemented): the daemon tracks per-consumer-pid
    generations for the env file and the hook file independently via
    `shell_registry`, and only tells a given consumer's prompt tick to re-source
    when that consumer's last-seen generation is behind the current one.
    Env/hook files are exposed through a stable current-symlink indirection
    (`env-<target>.sh`, `hook-<target>.sh` under the flake's state dir) that the
    daemon atomically repoints on every new eval, so the shell always sources
    the same path. `PromptResponse` is the wire contract between daemon and
    client for this protocol.

- Formalise the **shell adapter surface**: adding a new shell means (a)
  extending `ShellType`, (b) providing an activation snippet, (c) providing a
  spawn-command generator, (d) providing an env-file emitter. No other module
  changes.

## Impact

- **Affected specs**: `xi-devshell-activation` (new capability; first delta
  introduces its requirements).
- **Affected code**: `crates/xi-develop/src/activate.rs`,
  `crates/xi-develop/src/subshell.rs`, `crates/xi-develop/src/env_file.rs`,
  `crates/xi-develop/src/enter.rs`, `crates/xi-develop/src/shell.rs`, plus the
  previously-unlisted daemon-side half of the contract:
  `crates/xi-develop/src/daemon/server.rs` (response builder and
  `shell_registry` generation tracking),
  `crates/xi-develop/src/daemon/shell_registry.rs`,
  `crates/xi-develop/src/dirs.rs` (`current_link`), and
  `crates/xi-develop/src/hook/shortcut.rs` (`__XI_LOCK_HASH` reader with no
  current writer). Most static-module behaviour is already correct; the
  daemon-side protocol is already implemented but was entirely unspecified
  before this delta; `__XI_ORIG_PATH` and `__XI_LOCK_HASH` are genuine gaps
  needing either implementation or removal.
- **Coordination with `async-daemon-cqrs`**: the client-side shortcut path in
  `xi-devshell-daemon` is _intended_ to read `__XI_IN_DEVSHELL`,
  `__XI_FLAKE_ROOT`, and `__XI_LOCK_HASH`; this spec is the authoritative source
  for those variables' names and semantics, but note the `__XI_LOCK_HASH` writer
  gap above means the shortcut path cannot fire in production until that gap is
  closed.
- **Coordination with `devshell-trust-model`**: `xi develop activate` output
  never inspects the trust store; trust is checked at prompt-hook time inside
  the Rust binary. This spec's minimality clause enforces that separation.
- **Breaking?**: No. Env-var names, exit codes, and file layout are preserved
  from current behaviour. Removing or wiring the two dead/gap variables
  (`__XI_ORIG_PATH`, `__XI_LOCK_HASH`) is additive or cleanup, not a contract
  break, since no production code currently depends on either being set.
- **Migration**: None.

## Success Criteria

- **SC-A-001**: `xi develop activate bash|zsh|fish` output is at most 5 lines of
  shell code and contains no flake detection, no trust check, and no environment
  mutation beyond `PROMPT_COMMAND` / `precmd` / `fish_prompt` wiring.
- **SC-A-002**: Entering a devshell prepends nix paths to `$PATH` and leaves
  every pre-existing path entry present and in its original relative order.
- **SC-A-003**: Exiting a nested devshell (`depth=2`) cleans up exactly the
  depth-2 injected vars and leaves depth-1's env intact.
- **SC-A-004**: A shell whose CWD leaves the flake root causes the subshell to
  exit `200`; the parent does not set `__XI_SUPPRESS` and re-entry happens
  automatically on `cd` back in.
- **SC-A-005**: A user typing `exit` inside a **top-level** devshell (spawned
  directly off the real terminal shell by the `xi develop trust`-gated prompt
  hook) propagates that exit to the real shell, closing the terminal  -  it does
  not pop back to a bare prompt. A user typing `exit` inside a **nested**
  child-flake devshell causes the parent flake's shell to set
  `__XI_SUPPRESS=<child_flake_root>` and resume instead; the next prompt tick
  in the same location does NOT re-enter the child devshell until the user
  `cd`s out then back in.
- **SC-A-006**: `HOME`, `USER`, `SHELL`, `TERM`, `SSH_AUTH_SOCK`,
  `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`, and every other member of the full
  28-entry session-identity SKIP list are preserved from the parent env even
  when `nix print-dev-env` includes them.
- **SC-A-007**: `NIX_BUILD_TOP` and every other build-time nix var are absent
  from the interactive shell after activation.
- **SC-A-008**: Adding a new shell adapter requires code changes only to
  `shell.rs`, `activate.rs`, `subshell.rs`, and `env_file.rs`; no changes to
  `enter.rs`, `hook/`, or `daemon/` are required.
- **SC-A-009** (already true today, newly specified): a consumer whose last-seen
  env/hook generation is behind the daemon's current generation is told to
  re-source on its next prompt tick; a consumer already on the current
  generation is not.
- **SC-A-010** (gap, not yet met): `__XI_LOCK_HASH` is exported into the child
  shell's environment at activation time with the hash of `flake.lock`, so that
  `hook/shortcut.rs`'s fast path can actually compare it. Today no writer sets
  this variable outside test code, so the shortcut path can never take effect.
- **SC-A-011** (decision needed, tracked as a task): either `__XI_ORIG_PATH` is
  exported at first activation and used for an explicit PATH restoration, or the
  dead read of it in `trust.rs` is removed. Today it is read but never written,
  which is neither state.

## Assumptions

- Shell adapters remain the exhaustive dispatch pattern (`ShellType` enum); a
  plugin registry is out of scope.
- Nushell, elvish, and other non-POSIX-adjacent shells are out of scope for this
  delta; they can be added later without changing the contract.
- The prompt hook installed by `xi develop activate` is the only supported
  activation trigger. `direnv` integration is a separate concern and lives in
  its own future proposal.
- `nix print-dev-env --json` remains the authoritative source of the devshell
  env; changes to that upstream format are handled at the parser boundary
  (`env_file.rs::DevEnv`).
